# Course Vault 治理与审核方案

> 适用对象：`7620qwertqwert-beep/course-vault`（公开仓库、个人账号、学生维护者、无经费）。
> 当前基线：851 张课程卡片、基本没有真实资料、1 名维护者。
> 目标：把「恶意破坏、垃圾灌水、错误上传、版权隐私、Fork 回退、维护者误操作」六类事故挡在 `main` 之外；同时保证普通同学传一份资料仍然能在 10 分钟内完成。

## 0. 一页结论

### 0.1 三条铁律

| 铁律 | 为什么 | 怎么做 |
|---|---|---|
| **没有人直接 push `main`** | 破坏和误操作都只需要一次直推；PR 至少留下 diff、检查和讨论记录 | 开启分支保护；`main` 只接受 PR；管理员也纳入规则；急事走临时 break-glass，事后恢复 |
| **机器检查客观项，人只判断主观项** | 路径、体积、哈希、空文件、敏感词可以自动挡；版权、隐私、内容价值只能人看 | Actions 跑 `scripts/check.sh` + 路径/体积/删除数/重复哈希/索引；人工按固定顺序复核 |
| **先备份，再修复；能 revert 就不 reset** | 学生维护者也会误操作；`reset + force push` 会把别人的提交一起抹掉 | 本地裸仓库 + 每周 bundle；事故先用 `git revert`，只有泄露隐私/密钥才重写历史 |

### 0.2 分层结构

| 层 | 作用 | 本方案对应章节 |
|---|---|---|
| L0 账号与仓库基线 | 防止账号被接管、减少攻击面 | A.0、A.5 |
| L1 权限与分支保护 | 决定「谁能改什么、必须经过谁」 | A.1、A.2、A.3 |
| L2 自动化校验 | 挡住可机器判断的破坏和乱传 | B |
| L3 人工审核 | 判断版权、隐私、内容价值 | C |
| L4 备份与恢复 | 事故发生后把损失压到最小 | D |
| L5 分阶段治理 | 防止流程过重，没人愿意传 | E |

### 0.3 六类风险总表

| 风险 | 最可能入口 | 第一道防线 | 第二道防线 | 兜底 |
|---|---|---|---|---|
| 恶意破坏：删大量卡片、改 README 骂人、覆盖资料 | 被盗的协作者账号、Write 权限、直接 push | `main` 禁止直推；删除数上限；README 删除硬拦；CODEOWNERS | PR diff 人工看；覆盖已有文件必须说明 | 分支保护 + `git revert` + 历史恢复 + 撤销权限 |
| 垃圾灌水：无关文件、广告、大量空文件 | 上传表单、Fork PR | 路径白名单；空文件/可执行文件/超限压缩包拦截；文件数上限 | 人工看内容；广告/二维码/群链接直接拒 | 关闭 PR、限制互动、封禁账号、清理索引 |
| 错误上传：路径错、命名乱、整包上传、超 50MB | 填表上传 | `check.sh` 命名/结构；体积检查；压缩包体积/类型拦截 | 审核意见模板；维护者代改或要求重传 | 重命名/移动/拆分后重提；大文件转网盘链接 |
| 版权与隐私：禁传课件、含姓名学号原卷、个人信息实验报告 | 资料本身、PDF/Word 属性、扫描件 | 文本敏感词 + 文件名规则；表单必填脱敏确认，PR 必填来源/许可声明 | 人工逐页/逐属性检查；禁止外传一票否决 | 24h 临时下架、48h 删除；严重泄露重写历史并通知 fork |
| 好心办坏事：Fork 长期不更新，PR 覆盖新内容 | 陈旧 fork、网页上传同名文件 | 要求分支最新；修改已有文件触发复核；squash 合并 | 审核时看 `git diff main...PR` 而不是只看新增 | 冲突时由维护者按最新 `main` 解决；禁止整文件覆盖 |
| 维护者失误：误合并、误删分支、force push | 管理员操作、赶时间 | 管理员也走 PR；禁止 force push/删分支；合并前备份 | 合并后 24h 内自查；关键操作双人 | `git revert`、reflog/镜像恢复、GitHub Support |

## 1. 六类风险逐条对策

### 1.1 恶意破坏：删大量课程卡片、把 README 改成骂人话、覆盖别人的资料

**为什么有效：** 这类破坏通常不是「黑客突破」，而是拿到了 Write/Admin 的账号直接改，或者维护者误点。只要 `main` 不能直推、删除有硬上限、README 删除单独拦截，单次 PR 最多只能造成很小且可 revert 的破坏；历史备份保证内容能找回。

| 层次 | 具体做法 | 为什么 |
|---|---|---|
| 权限 | 普通同学走上传表单（Issue），不直接给写权限；Fork 只作进阶备选；Write 只给 2–3 个可信的人；Admin 只留 owner | 减少可破坏账号数量；表单由机器人落到新分支，普通同学对 `main` 没有写权限 |
| 分支 | `main` 开 PR 保护、禁止 force push、禁止删除；管理员也纳入 | 一次直推就能删 851 个卡片；PR + 检查把操作变成可审计事件 |
| 自动化 | 单 PR 删除文件 > 5 个直接失败；删除任何 `courses/**/README.md` 直接失败；修改已有文件打 `modified` 警告 | 恶意批量删除和最值钱的课程卡片最先被挡住 |
| 审核 | 覆盖已有文件必须说明「为什么覆盖」；只看新增文件不算审核 | 覆盖别人后提交的内容是最容易被漏掉的破坏方式 |
| 恢复 | 先 `git revert` 合并提交；卡片从删除前一个提交恢复；保留 90 天镜像 | 不重写历史也能快速恢复，且不影响别人 fork |
| 追责 | 撤销协作者权限、检查账号 2FA/会话、保留 PR 和 commit 链接 | 如果是账号被盗，改密码不够，必须踢掉旧会话 |

**直接拒收：** 任何删除课程卡片、批量删除资料、把 README 改成侮辱/广告内容、恶意覆盖他人文件的 PR。不要「先合并再修」。

### 1.2 垃圾灌水：无关文件、广告、大量空文件把仓库撑爆

**为什么有效：** 灌水的成本低，但特征很明显：空文件、超限压缩包、可执行文件、大量小文件、与课程无关的图片/二维码。自动检查可以把这些挡在人工审核之前；人工只需要判断「是否与这门课有关」。

| 层次 | 具体做法 | 为什么 |
|---|---|---|
| 路径 | 普通 PR 只允许改 `courses/` 下路径 | 不允许借 PR 改首页、脚本、Workflow、LICENSE |
| 体积 | 单文件 ≤ 50 MiB；单 PR 总新增 ≤ 100 MiB；单 PR 文件数 ≤ 200；0 字节文件直接失败 | 防止「大量空文件」和「一次塞满仓库」 |
| 类型 | 允许 `.zip`（≤20MB）；禁止 `.7z/.rar/.tar/.gz/.iso/.exe/.msi/.apk/.bat/.cmd/.ps1/.docm/.xlsm/.pptm` 等 | 超限压缩包无法逐页审核，也可能是压缩炸弹；宏文档可能带恶意代码 |
| 内容 | 广告、二维码、拉群、兼职、代考、代写、与课程无关的文件直接拒 | 这些不是「资料」，会迅速把库变成广告板 |
| 账号 | 短时间大量 PR/Issue 时开 `Settings → Moderation → Interaction limits`（24 小时/3 天/1 周） | GitHub 原生限制互动，不需要写代码；攻击结束后关闭 |
| 清理 | 关闭 PR、删除分支、必要时 block 用户；索引和课程卡片同步清理 | 只删文件不删索引会留下死链和广告文本 |

**注意：** 不要用「必须已有贡献者才能开 Issue」来挡灌水——新同学本来就是潜在贡献者，这会直接掐死供给。用模板、标签、互动限制和人工分诊更现实。

### 1.3 错误上传：路径放错、命名乱来、整包上传、超 50MB

**为什么有效：** 这类问题大多不是恶意，作者愿意改。自动检查给出明确错误，审核用固定话术要求重传，比直接关闭更省时间。

| 问题 | 自动/人工处理 | 为什么 |
|---|---|---|
| 路径错 | 公共课必须是 `courses/公共课/<课名>/`；专业课必须是 `courses/专业课/<学院>/<专业>/<课名>/` | 目录层级错了，索引和后续检索都会错位 |
| 命名乱 | 文件名必须匹配 `^20[0-9]{2}(春|秋)-(期末|期中|笔记|作业|实验报告|实验|课件|复习|答案)-` | 统一命名才能在 1000 门课里按学期/类型筛选 |
| 整包上传 | 压缩包仅收 ≤20MB；要求解压后按类型放，或只传一个 PDF | 压缩包不能预览、不能逐页查隐私，也容易夹带可执行文件 |
| 超 50MB | 拒绝；要求压缩、拆分，或网盘链接 + 课程卡片登记 | GitHub 单文件硬上限 100 MiB，仓库越大 clone 越慢；50 MiB 是本库自设线 |
| 缺课程卡片/子目录 | 要求补齐 `README.md` 和 `笔记/课件/试卷/作业` | 卡片比资料更值钱；没有卡片的资料无法判断适用学期和老师 |
| 内容重复 | 同一 PR 内完全相同内容直接失败；与库内重复给出警告 | 重复文件浪费体积，也会让索引出现两个「同一份资料」 |

**处理原则：** 能改就要求改；作者 14 天不回应再关闭。维护者可以代改文件名/移动目录，但**不要替作者判断版权和隐私**。

### 1.4 版权与隐私事故：禁传课件、含姓名学号原卷、含个人信息的实验报告

**为什么有效：** 这类内容一旦公开，删当前文件也不等于删历史，fork 和缓存可能还在。所以必须在合并前挡；合并后只能「先下架、再清理历史、再通知」。

| 类型 | 规则 | 为什么 |
|---|---|---|
| 老师明确说「不得外传」的课件/讲义 | **一票否决**，不讨论「学习交流」 | 明确禁止外传就是最直接的权利人意思表示；合并后再删也会留下历史 |
| 未公开试卷、教师用书、教材 PDF | 不收；教材只登记书名、作者、版次、ISBN | 这些通常是有明确版权的整本作品，不属于「同学原创」 |
| 含姓名/学号/成绩的原卷 | 不收；只收空白卷或彻底脱敏的版本 | 姓名+学号+成绩是典型的个人信息组合，公开即事故 |
| 含个人信息的实验报告 | 必须删除姓名、学号、组员、老师评语、联系方式、文档属性/批注/修订记录 | 页眉页脚、Word 作者、PDF 元数据、截图角落都经常漏 |
| 第三方图片/表格/论文 | 要求来源和许可；无许可就删掉或换自制图 | 同学原创笔记的 CC 许可不能覆盖里面抄来的图表 |
| 投诉 | 24 小时内确认并临时下架，48 小时内完成删除 | 先止损，再讨论；不要要求投诉人先公开身份 |

**为什么不能只靠敏感词：** 扫描件、图片、PDF 里的姓名是像素，不是文本；Word 的属性、批注、修订记录也不一定出现在正文。自动检查只能报警，最终必须人工看。

### 1.5 好心办坏事：Fork 后长期不更新，PR 覆盖别人后提交的新内容

**为什么有效：** 网页上传最容易发生的不是「故意覆盖」，而是作者的 fork 停在三个月前，上传同名文件时把上游后来的版本盖掉。要求分支最新 + 覆盖已有文件必须复核 + squash 合并，可以把「静默回退」变成「可见的 diff」。

| 措施 | 怎么做 | 为什么 |
|---|---|---|
| 要求分支最新 | 分支保护开 `Require branches to be up to date before merging`；PR 页面点 `Update branch` | 合并前强制把最新 `main` 合进来，冲突会暴露 |
| 覆盖已有文件要说明 | 自动化对 `M`（修改）和 `R`（重命名）打警告；PR 模板要求写「为什么覆盖」 | 新增文件通常安全，覆盖才是回退高发区 |
| 看三点 diff | 审核时看 `git diff main...PR`、文件状态（A/M/D/R）、以及被修改文件的原内容 | 只看「Files changed」里的新增行，容易漏掉删除和替换 |
| squash 合并 | 仓库只开 `Allow squash merging`，关闭 merge commit/rebase | 一个 PR 一个提交，回退简单，历史不会被 fork 的多个提交搅乱 |
| 冲突处理 | 维护者拉最新 `main` 到本地，按文件逐个解决；禁止用「整份文件选 ours/theirs」代替判断 | 整文件选一边会无声丢掉另一边的更新 |
| 合并后删分支 | 开 `Automatically delete head branches` | 减少陈旧分支和误用旧分支再次提交 |

**给贡献者的同步命令（只动自己的分支，不动 `main`）：**

```bash
git remote add upstream https://github.com/7620qwertqwert-beep/course-vault.git
git fetch upstream
git switch main
git merge --ff-only upstream/main
git push origin main

# 如果是在功能分支上，用 rebase 把自己的提交放到最新 main 之后
git switch my-upload
git rebase upstream/main
git push --force-with-lease origin my-upload   # 只允许对自己的功能分支这样做
```

### 1.6 维护者自己失误：误合并、误删分支、force push 搞坏历史

**为什么有效：** 维护者不是敌人，但一个人长期操作一定会出错。把「不可逆操作」从日常流程里删掉：不直推、不 force、不删 `main`；合并前有备份；出错后用 revert/reflog/镜像恢复，而不是继续用破坏性命令掩盖。

| 失误 | 立即动作 | 不要做什么 |
|---|---|---|
| 误合并 | 在 PR 页面点 `Revert`（会生成新 PR），或本地 `git revert -m 1 MERGE_SHA` | 不要 `git reset --hard` 后 force push `main` |
| 误删文件 | 从删除前一个提交 `git restore --source=DELETE_SHA^1 -- PATH` | 不要凭记忆重写文件；不要先清空历史 |
| 误删分支 | 从本地 reflog、镜像裸仓库、PR 的 `refs/pull/<n>/head` 恢复成新分支 | 不要在原分支上继续强推；先恢复成 `rescue/...` |
| 误 force push | 先备份当前 `.git`，再从 reflog/镜像找旧 SHA，恢复成 rescue 分支 | 不要再次 force push 覆盖证据 |
| 账号被盗 | 改密码、撤销会话、移除协作者、检查 Actions/Deploy keys/Webhooks | 不要只在 PR 里 revert，账号还在攻击者手里 |

**日常预防：** 管理员也纳入分支保护；合并前跑检查；每周做一次镜像；每季度做一次恢复演练；任何「重写历史」操作先备份并记录原因。

## 2. A. GitHub 仓库设置层（照着点）

> 下面以网页端英文界面为准，括号内是中文含义。GitHub 会改 UI 文案，找不到时用仓库地址后的路径直达：
> `https://github.com/7620qwertqwert-beep/course-vault/settings`

### 2.1 A.0 账号与仓库基线

| 设置 | 网页路径 | 建议值 | 为什么 |
|---|---|---|---|
| 双因素认证 | 个人 `Settings → Password and authentication` | 开启 Passkey/2FA，恢复码离线保存 | 维护者账号是最高价值目标；只靠密码会被撞库/钓鱼 |
| 登录会话 | 个人 `Settings → Sessions` | 定期撤销不认识的会话 | 被盗后改密码不一定踢掉旧会话 |
| 仓库可见性 | `Settings → General → Danger Zone` | 保持 Public | 公开仓库才有免费 Actions/分支保护，也符合共享库定位 |
| 默认分支 | `Settings → General → Default branch` | `main` | 所有保护和文档都围绕 `main` |
| Wiki | `Settings → General → Features` | 关闭 | Wiki 是另一个可被乱写的入口，当前不需要 |
| Projects | `Settings → General → Features` | 关闭 | 一个人维护，少一个看板少一份负担 |
| Issues | `Settings → General → Features` | 开启 | 主上传通道（表单）+ 投诉入口；不用 Fork |
| Discussions | `Settings → General → Features` | 现在关闭；中期再开 | 0 资料阶段开两个社区入口只会增加审核负担 |
| Sponsorships | `Settings → General → Features` | 关闭 | 非营利、无经费，不引入收款和税务问题 |
| 自动删除头分支 | `Settings → General → Pull Requests` | 开启 | 合并后清理分支，减少陈旧 fork 误用 |
| 合并方式 | `Settings → General → Pull Requests` | 只开 `Allow squash merging`；关闭 merge commit 和 rebase | 一个 PR 一个提交，回退简单 |
| 自动更新提示 | 同上 | 开启 `Always suggest updating pull request branches` | 提醒作者分支落后，降低覆盖风险 |
| Auto-merge | 同上 | 开启；只给 `approved` 的归档 PR | 机器人归档后自动合并；CI 不过不会合 |
| 删除/转移仓库 | `Settings → General → Danger Zone` | 不操作；如必须，先做 bundle 备份 | 这是不可逆操作，不能在日常流程里出现 |

### 2.2 A.1 协作者权限：Read / Triage / Write / Maintain / Admin

**先记住一句话：权限角色决定「能不能改仓库」，分支保护决定「能不能改 `main`」。** 即使给了 Write，只要 `main` 开了 Require PR，也不能直接推 `main`。

| 角色 | 能做什么（与本库相关） | 能直接 push `main`？ | 能改仓库设置？ | 建议给谁 | 为什么 |
|---|---|---|---|---|---|
| **Read** | 查看/克隆/下载、开 Issue、评论、从 Fork 提 PR、看 Releases | 否 | 否 | 普通同学、只读审稿人、课程顾问 | 最小权限；提 PR 不需要 Write |
| **Triage** | Read 的全部 + 给 Issue/PR 打标签、指派、关闭/重开、标记重复、请求评审、管理里程碑；不能改代码、不能合并 | 否 | 否 | 社区值班、Issue 分诊志愿者 | 能处理垃圾 Issue，又碰不到代码 |
| **Write** | Read/Triage 的全部 + 推普通分支、建/改文件、开 PR、在保护规则允许时合并、发 Release；不能管理访问、分支保护、计费 | 受保护时否；未保护分支可以 | 仅部分内容设置，不能管理访问/保护规则 | 可信上传者、课程负责人、活跃审核人 | 足够日常贡献；`main` 仍受保护 |
| **Maintain** | Write 的全部 + 日常仓库设置、Issues/PR/Release/分支管理；不能转移/删除仓库、改可见性、管理协作者、访问计费/敏感密钥 | 受保护时否 | 日常设置，不含敏感操作 | 核心维护者（中期 2–3 人） | 分担维护工作，但不给「核按钮」 |
| **Admin** | 全部，包括删除/转移仓库、改可见性、管理协作者、分支保护、Actions secrets、计费 | 规则允许时可绕过；本方案要求也走 PR | 全部 | 仅 owner；后期最多 2–3 人 | 最高权限只给必要的人 |

**网页操作：** `Settings → Access → Collaborators and teams → Add people`，输入 GitHub 用户名，选角色，发送邀请。

**本库目标状态：**

| 阶段 | Admin | Maintain | Write | Triage | Read |
|---|---|---|---|---|---|
| 现在（1 人） | owner 1 人 | 0 | 0 | 0 | 不主动加 |
| 中期（10 贡献者） | 1–2 | 2–3 | 2–4 | 1–2 | 按需 |
| 后期（全校） | 2–3 | 每学院/大类 1–2 | 课程负责人若干 | 值班若干 | 按需 |

**为什么现在不加 Write：** 目前没有真实资料，也没有经过至少几次完整贡献的 contributor。普通上传走表单，维护者用归档 PR 记录观察；连续 3 次高质量贡献后再考虑给 Write/Triage。

### 2.3 A.2 `main` 分支保护：建议值

**网页路径（经典分支保护）：** `Settings → Branches → Branch protection rules → Add branch protection rule`。
**网页路径（新版规则集）：** `Settings → Rules → Rulesets → New branch ruleset`，Target 选 `main`，Enforcement 选 `Active`，Bypass list 留空。

| 设置 | 现在（1 人） | 中期（10 人） | 后期（全校） | 为什么 | 怎么设置 |
|---|---|---|---|---|---|
| Branch name pattern | `main` | `main` | `main` | 只保护主分支；其他分支可自由试错 | 新建规则，pattern 填 `main` |
| **Require a pull request before merging** | **开** | **开** | **开** | 所有改动留 diff、检查、讨论；直推没有这些 | 勾选；管理员也纳入 |
| Required approvals | **0** | **1** | **1**（日常）；治理类人工要求 2 | 1 人时要求 1 个批准会死锁（不能自批）；有第二人后必须有人看 | `Require approvals` 数字 |
| Dismiss stale approvals | **开** | **开** | **开** | 批准后作者再推恶意提交，旧批准应失效 | `Dismiss stale pull request approvals when new commits are pushed` |
| Require approval of most recent push | **开** | **开** | **开** | 防止「先批准、后塞东西」 | `Require approval of the most recent reviewable push` |
| Require review from Code Owners | **关**（现在只有 owner） | **开** | **开** | 课程/目录变更应由对应负责人看；现在开会让 owner 自己的 PR 卡住 | `Require review from Code Owners`；先配好 CODEOWNERS |
| Require status checks | **开**（workflow 跑过一次后） | **开** | **开** | 机器先挡路径/体积/删除数/重复/索引 | 搜索并勾选 `path-policy`、`content-check`、`index-dedupe` |
| Require branches up to date | **开** | **开** | **开** | 防止陈旧 fork 覆盖后来提交 | `Require branches to be up to date before merging`；PR 页点 `Update branch` |
| Require conversation resolution | **开** | **开** | **开** | 审核提出的问题必须解决，不能带着未答问题合并 | 勾选 `Require conversation resolution before merging` |
| Require linear history | **开** | **开** | **开** | 配合 squash，回退简单 | 勾选；关闭 merge commit/rebase |
| Require signed commits | **关** | **关** | 可选 | 网页上传用户很多没有签名，强开会赶走贡献者 | 后期有明确安全要求再开 |
| Do not allow bypassing | **开**（workflow 稳定后） | **开** | **开** | 管理员误操作同样危险；但必须配 break-glass | 勾选 `Do not allow bypassing the above settings` |
| Allow force pushes | **关** | **关** | **关** | force push 会覆盖别人提交，是最危险的操作 | 不勾选；任何人都不允许 |
| Allow deletions | **关** | **关** | **关** | 防止整个 `main` 被删 | 不勾选 |
| Restrict who can push | owner / `maintainers` | `maintainers` | `maintainers` | 即使 PR 规则失效，也只剩少数人能推 | `Restrict who can push to matching branches` |
| Lock branch | **关** | **关** | **关** | 锁死会连 PR 都不能合；只在极端攻击时临时用 | 不勾选 |

**关键解释：**

- **现在 approvals 为什么是 0：** 只有 1 个维护者时，GitHub 不允许作者批准自己的 PR；要求 1 个批准会让所有 PR 永远卡住。0 批准 + 必过检查 + 归档 PR 由机器人自动合并、其他 PR 由 owner 合并，是现阶段唯一能跑通的组合。
- **中期为什么是 1：** 有第二个有 Write 权限的人后，任何 PR 都能找到非作者的批准者。不要一上来要 2 个，10 个贡献者时凑不齐。
- **后期为什么日常还是 1：** 上千门课时，2 个批准会成为瓶颈；高风险目录用 CODEOWNERS + 人工「治理类 2 人」规则补，不把全库拖慢。
- **`Do not allow bypassing` 的代价：** Actions 故障时管理员也合不了。必须按 D.8（5.8）的 break-glass 临时关闭规则，事后恢复；不能长期留 bypass 名单。

**规则集（Rulesets）对应项：**

| 经典分支保护 | Rulesets 里的名字 |
|---|---|
| Require a pull request before merging | Require a pull request before merging |
| Required approvals | Required approvals（在 PR 规则里） |
| Dismiss stale approvals | Dismiss stale pull request approvals |
| Require review from Code Owners | Require review from Code Owners |
| Require status checks | Require status checks to pass |
| Require branches up to date | Require branches to be up to date before merging |
| Require conversation resolution | Require conversation resolution before merging |
| Require linear history | Require linear history |
| Allow force pushes | Block force pushes |
| Allow deletions | Restrict deletions |
| Do not allow bypassing | Bypass list 留空 + Enforcement Active |

### 2.5 A.4 Issues 与 Discussions：开不开、怎么限制

**先说事实：GitHub 公开仓库没有「只允许已有贡献者开 Issue」这个原生开关。** 有 Read 权限的人（包括刚注册的陌生人）都可以开 Issue；能做的只是模板、标签、互动限制、人工关闭。不要为了「限制」去装一个需要付费/高权限的 App。

| 渠道 | 现在 | 中期 | 后期 | 为什么 |
|---|---|---|---|---|
| Issues | **开** | 开 | 开 | 主上传通道（表单）+ 投诉入口；也是审核记录 |
| Discussions | **关** | **开** | 开 | 现在没人运营，开两个入口只会两边都荒；中期用来放 Q&A/公告，Issue 只做上传/投诉 |
| Wiki | 关 | 关 | 关 | 另一个可写入口，没有精力维护 |
| Projects | 关 | 可选 | 可选 | 一个人时看板是负担；后期 PR 多再用 |

**限制垃圾 Issue 的可落地做法：**

1. `Settings → General → Features → Issues` 保持开启；只保留「上传资料」表单和投诉入口，关闭空白 Issue。
2. 表单必填：课程类别、学院/专业（专业课）、课程名称、年份学期、资料类型、附件、脱敏确认；少一项不能提交。
3. 给模板自动打 `status:new` + `type:upload` 标签（Issue Forms 的 `labels:` 字段）。
4. 维护者 48 小时内分诊：填表上传的确认后加 `approved` 交给机器人；广告/无关内容直接关闭并 `Report abuse`。
5. 遇到集中攻击：`Settings → Moderation → Interaction limits` 选 24 小时/3 天/1 周，限制为「已有账户」或「仅协作者」；攻击结束后关闭。
6. 不要公开收集个人信息；投诉走邮箱或 Private vulnerability reporting。**普通 Issue 不是私密的**，现有 TAKEDOWN 里「私密 Issue」的说法应改成「非公开渠道」。

**什么时候开 Discussions：** 至少 3 个活跃贡献者、每周有 2 个以上非 PR 问题、维护者能固定每周看一次时。分类建议：

| 分类 | 谁能发 | 用途 |
|---|---|---|
| Announcements | 仅维护者 | 规则变更、下架公告、维护窗口 |
| Q&A | 所有人 | 上传/使用问题；答案可被后来人搜到 |
| Course requests | 所有人 | 求某门课资料，不贴个人信息 |
| Showcase | 所有人 | 笔记/复习方法分享，不替代 PR |

### 2.6 A.5 CODEOWNERS：按目录分派审核

**文件位置：** `.github/CODEOWNERS`（推荐）或根目录 `CODEOWNERS`。
**网页路径：** 文件合并后，`Settings → Branches → 编辑 main 规则 → Require review from Code Owners` 勾选；规则集在 PR 规则里勾。
**语法要点：**

- 一行一个 pattern + owner；`@username` 或个人仓库；`@org/team` 需要组织且团队有 Write。
- **最后匹配的 pattern 生效**，所以先写宽泛的 `*`，再写具体目录。
- Code owner 必须有 Write 权限，否则不会被自动请求，也无法满足「Require review from Code Owners」。
- 只有 1 个 owner 时不要开强制 Code Owner 审核：作者不能批准自己的 PR，会死锁。

**现在（1 人）可用版本：**

```gitignore
# .github/CODEOWNERS
# 顺序：宽 -> 窄；最后匹配者生效。
# 现在只有 owner，主要作用是留下目录归属，暂不开强制 Code Owner 审核。

*                                   @7620qwertqwert-beep

/courses/                            @7620qwertqwert-beep
/courses/公共课/                     @7620qwertqwert-beep
/courses/专业课/                     @7620qwertqwert-beep
/courses/**/README.md                @7620qwertqwert-beep

# 治理文件：任何改动都必须 owner 看
/.github/                            @7620qwertqwert-beep
/scripts/                            @7620qwertqwert-beep
/LICENSE                             @7620qwertqwert-beep
/TAKEDOWN.md                         @7620qwertqwert-beep
/INDEX.md                            @7620qwertqwert-beep
```

**中期（有团队/多个审核人后）示例：**

```gitignore
# .github/CODEOWNERS
*                                           @7620qwertqwert-beep

# 公共课：一个公共课审核组
/courses/公共课/                             @course-vault/public-reviewers

# 专业课按学院/专业分派；团队需有 Write 权限
/courses/专业课/医学院/                       @course-vault/med-reviewers
/courses/专业课/医学院/护理学/                @course-vault/nursing-reviewers
/courses/专业课/计算机与信息技术学院/          @course-vault/cs-reviewers

# 课程卡片和治理文件始终由核心维护者兜底
/courses/**/README.md                        @7620qwertqwert-beep
/.github/                                    @7620qwertqwert-beep
/scripts/                                    @7620qwertqwert-beep
/LICENSE                                     @7620qwertqwert-beep
/TAKEDOWN.md                                 @7620qwertqwert-beep
/INDEX.md                                    @7620qwertqwert-beep
```

**分派原则：**

| 目录 | 谁审 | 为什么 |
|---|---|---|
| `courses/公共课/` | 公共课审核组 | 高数/英语等量大、同名课多，统一口径 |
| `courses/专业课/<学院>/` | 对应学院审核组 | 专业内容外行看不出错误，也看不出是否泄露临床隐私 |
| `courses/**/README.md` | 核心维护者 | 卡片是索引和课程信息入口，最容易被乱改 |
| `.github/`、`scripts/`、`LICENSE`、`TAKEDOWN.md`、`INDEX.md` | owner/核心维护者 | 治理文件被改等于改规则，不能由普通 PR 碰 |
| 新增专业/学院 | 核心维护者 + 该专业审核人 | 目录结构一旦定错，后续大量文件跟着错 |

## 3. B. 自动化校验层

### 3.1 检查清单：哪些必须失败，哪些只警告

> 下表是目标规则。当前 `.github/workflows/check.yml` 已实现目录/命名/体积/空文件/索引/PII 等基础项；PR 触发时 `check.sh` / `build_index.py` 固定取自 base 分支，路径白名单与治理文件改动已改为阻断，单 PR 总体积上限 100 MiB；删除数上限目前仍为 20 个（目标 5 个）。详见文末「已实施状态」。

| 检查 | 具体规则 | 失败/警告 | 为什么 |
|---|---|---|---|
| 现有自检 | 用 **base 分支的** `scripts/check.sh` 跑目录结构、命名、50MB、文本 PII | 失败 | 不能执行 PR 里被改过的脚本，否则攻击者改脚本就能绕过 |
| 路径白名单 | 普通 PR 只允许 `courses/**`；根目录文件、`docs/`、`scripts/`、`.github/`、`LICENSE` 等只允许 owner 的 `type:governance` PR | 失败 | 防止借上传改 workflow、README、协议、脚本 |
| 敏感文件 | `.github/workflows/**`、`LICENSE` 任何普通 PR 改动直接失败 | 失败 | 这两个是「改规则/改授权」的最高风险文件 |
| 符号链接/子模块 | 拒绝 `120000` symlink、`160000` submodule | 失败 | 可指向仓库外路径，或把审核引到别处 |
| 文件体积 | 单文件 > 50 MiB 失败；单 PR 新增 > 100 MiB 失败 | 失败 | 保护 clone 速度，守住 GitHub 100 MiB 硬上限之前 |
| 空文件 | 0 字节失败 | 失败 | 「大量空文件撑爆仓库」的最直接特征 |
| 文件数 | 单 PR > 200 个文件失败；> 50 个警告 | 失败/警告 | 大批量变更必须人工拆分 |
| 删除数 | 单 PR 删除 > 5 个文件失败；删除 `courses/**/README.md` 失败；任何删除/重命名默认失败，带 `type:cleanup` 才放行并警告 | 失败 | 普通上传默认只接受新增（A）；恶意删卡/删资料的第一道硬拦 |
| 压缩包/可执行 | 后缀 + magic bytes 双重检查：zip 超过 20MB 拒绝；7z/rar/tar/gz/iso/exe/msi/apk/bat/cmd/ps1/docm/xlsm/pptm 等拒绝 | 失败 | 不能逐页审核，且可能带宏/病毒/压缩炸弹 |
| 重复哈希 | 同一 PR 内 Git blob 完全相同失败；维护者加 `dup-ok` 后可降为警告；与库内已有文件重复只警告 | 失败/警告 | 防止同一份资料反复占空间；跨课程重复可能合理，所以留人工例外 |
| 个人信息（文本） | 新增文本中出现「学号 + 6 位以上数字」、18 位身份证、11 位手机号等 | 失败 | 这些是最典型的明文个人信息 |
| 个人信息（文件名） | 文件名含 `学号/身份证/个人/成绩单` 或连续 8 位以上数字 | 失败 | 文件还没打开就能看出风险 |
| 敏感词 | 新增文本含「禁止外传/不得外传/内部资料/机密/教师用书/教材全本」 | 失败（转人工） | 不是所有命中都违规，但必须让人看一眼 |
| 索引一致性 | 运行 `python3 scripts/build_index.py --check`，`INDEX.md` 必须与课程目录自动生成结果完全一致（`--check` 复用旧时间戳行，不会因生成时间不同而误报） | 失败 | 死链、漏课和手改索引都会被发现；新增课程后必须重新生成 `INDEX.md` |
| PR 模板 | 必填来源/许可/脱敏/只改 `courses/` | 人工 | 自动检查无法判断声明真假，但能固定审核证据 |

### 3.2 关键 workflow 片段（只展示，不创建文件）

> 放到 `.github/workflows/governance.yml` 时，必须先走 owner 的 `type:governance` PR，合并前人工复核。
> **不要用 `pull_request_target` 去 checkout PR 代码**；不要给 `contents: write`；不要把任何 secret 暴露给 fork PR。
> 示例用 `actions/checkout@v4` 便于阅读；正式启用前把 action 锁到完整 commit SHA。

```yaml
name: governance

on:
  pull_request:
    branches: [main]

permissions:
  contents: read

concurrency:
  group: governance-${{ github.event.pull_request.number }}
  cancel-in-progress: true

jobs:
  path-policy:
    name: path-policy
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0
          persist-credentials: false

      - name: Enforce path, deletion and size policy
        env:
          BASE_SHA: ${{ github.event.pull_request.base.sha }}
          HEAD_SHA: ${{ github.event.pull_request.head.sha }}
          PR_LABELS: ${{ join(github.event.pull_request.labels.*.name, ',') }}
          AUTHOR_ASSOCIATION: ${{ github.event.pull_request.author_association }}
        run: |
          set -euo pipefail
          python3 - <<'PY'
          import os
          import subprocess
          import sys

          base = subprocess.check_output(
              ["git", "merge-base", os.environ["BASE_SHA"], os.environ["HEAD_SHA"]],
              text=True,
          ).strip()
          head = os.environ["HEAD_SHA"]
          labels = {x.strip() for x in os.environ.get("PR_LABELS", "").split(",") if x.strip()}
          owner_governance = (
              os.environ.get("AUTHOR_ASSOCIATION") == "OWNER"
              and "type:governance" in labels
          )

          raw = subprocess.check_output(
              ["git", "diff", "--name-status", "-z", base, head]
          )
          parts = raw.split(b"\0")
          changes = []
          i = 0
          while i < len(parts):
              if not parts[i]:
                  i += 1
                  continue
              status = parts[i].decode("utf-8", "replace")
              i += 1
              if status[:1] in ("R", "C"):
                  old = parts[i].decode("utf-8", "replace")
                  new = parts[i + 1].decode("utf-8", "replace")
                  i += 2
                  changes.append((status[:1], old, new))
              else:
                  path = parts[i].decode("utf-8", "replace")
                  i += 1
                  changes.append((status[:1], path, path))

          errors = []
          warnings = []
          deleted = []
          added_or_modified = []
          total_new_bytes = 0

          max_file = 50 * 1024 * 1024
          max_total = 100 * 1024 * 1024
          max_files = 200
          max_deletes = 5

          blocked_ext = {
              "7z", "rar", "tar", "gz", "tgz", "bz2", "xz",
              "iso", "dmg", "exe", "msi", "apk", "bat", "cmd", "ps1",
              "vbs", "jar", "class", "pyc", "o", "a", "so", "dll", "dylib",
              "docm", "xlsm", "pptm",
          }
          office_zip_ext = {"docx", "pptx", "xlsx", "odt", "ods", "odp"}

          def git_size(path):
              return int(subprocess.check_output(
                  ["git", "cat-file", "-s", f"{head}:{path}"], text=True
              ).strip())

          def first_bytes(path, n=8):
              proc = subprocess.Popen(
                  ["git", "show", f"{head}:{path}"],
                  stdout=subprocess.PIPE,
                  stderr=subprocess.DEVNULL,
              )
              data = proc.stdout.read(n)
              proc.stdout.close()
              proc.wait()
              return data

          for status, old, new in changes:
              if status == "D":
                  deleted.append(old)
                  if old.startswith("courses/") and old.endswith("/README.md"):
                      errors.append(f"禁止删除课程卡片：{old}（课程下架请走治理 PR）")
                  continue

              if status in ("R", "C"):
                  paths = [new]
                  if status == "R":
                      # 重命名等于删旧路径 + 加新路径；按删除计数，防止用重命名绕过删除上限。
                      deleted.append(old)
                  if old.endswith("/README.md"):
                      errors.append(f"禁止重命名/替换课程卡片：{old}")
              else:
                  paths = [new]

              for path in paths:
                  if status == "M":
                      warnings.append(f"修改已有文件，请确认没有覆盖后来提交的内容：{path}")
                  if not path.startswith("courses/"):
                      if owner_governance:
                          warnings.append(f"治理 PR 修改了课程外路径：{path}，请人工确认")
                      else:
                          errors.append(
                              f"普通 PR 只允许改 courses/ 下路径；发现：{path}。"
                              "根目录/Workflow/LICENSE 等请走 owner 的 type:governance PR。"
                          )
                      if path.startswith(".github/workflows/") or path == "LICENSE":
                          if not owner_governance:
                              errors.append(f"敏感文件禁止普通 PR 修改：{path}")

                  if path.startswith("courses/"):
                      parts = path.split("/")
                      if any(part in ("", ".", "..") for part in parts):
                          errors.append(f"非法路径（空段/./..）：{path}")
                      if "\\" in path or any(ord(ch) < 32 for ch in path):
                          errors.append(f"路径含反斜杠或控制字符：{path}")
                      if len(path) > 240:
                          warnings.append(f"路径过长（>240 字符）：{path}")

                  ext = path.rsplit(".", 1)[-1].lower() if "." in path else ""
                  if ext in blocked_ext:
                      errors.append(f"禁止上传可执行/宏/不支持的压缩格式：{path}（.{ext}）")
                      continue
                  if ext == "zip" and git_size(path) > 20 * 1024 * 1024:
                      errors.append(f"压缩包超过 20MB：{path}")
                      continue

                  # 类型/符号链接：120000 = symlink，160000 = submodule
                  tree = subprocess.check_output(
                      ["git", "ls-tree", head, "--", path], text=True
                  ).strip()
                  if tree:
                      mode = tree.split()[0]
                      if mode in ("120000", "160000"):
                          errors.append(f"禁止 symlink/submodule：{path}")
                          continue

                  size = git_size(path)
                  if size == 0:
                      errors.append(f"禁止 0 字节空文件：{path}")
                  if size > max_file:
                      errors.append(f"单文件超过 50 MiB：{path}（{size} 字节）")
                  total_new_bytes += size
                  added_or_modified.append(path)

                  magic = first_bytes(path)
                  if magic.startswith(b"MZ") or magic.startswith(b"\x7fELF"):
                      errors.append(f"禁止上传可执行文件：{path}")
                  if magic.startswith((b"PK\x03\x04", b"7z\xbc\xaf", b"Rar!", b"\x1f\x8b")) \
                          and ext not in office_zip_ext:
                      errors.append(f"文件内容像压缩包，但扩展名不是允许的 Office 文档：{path}")

          if len(changes) > max_files:
              errors.append(f"单 PR 改动文件过多：{len(changes)} > {max_files}，请拆分")
          elif len(changes) > 50:
              warnings.append(f"单 PR 改动文件较多：{len(changes)}，请确认不是批量灌水")
          if len(deleted) > max_deletes:
              errors.append(f"单 PR 删除文件过多：{len(deleted)} > {max_deletes}，必须人工拆分/说明")
          elif deleted:
              warnings.append(f"本 PR 删除/重命名 {len(deleted)} 个文件：{', '.join(deleted)}")
              if "type:cleanup" not in labels and "type:governance" not in labels:
                  errors.append(
                      "本 PR 含删除/重命名：普通上传 PR 默认只接受新增（A）；"
                      "请由维护者确认并加 type:cleanup 标签，或拆成治理 PR。"
                  )
          if total_new_bytes > max_total:
              errors.append(f"单 PR 新增内容超过 100 MiB：{total_new_bytes} 字节")

          if errors:
              for message in errors:
                  print(f"::error::{message}")
              print(f"共 {len(errors)} 项阻断问题。")
              sys.exit(1)

          for message in warnings:
              print(f"::warning::{message}")
          print(f"通过：{len(changes)} 个变更，{len(added_or_modified)} 个新增/修改文件。")
          PY
```

```yaml
  index-dedupe:
    name: index-dedupe
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0
          persist-credentials: false

      - name: Check INDEX links and duplicate content
        env:
          BASE_SHA: ${{ github.event.pull_request.base.sha }}
          HEAD_SHA: ${{ github.event.pull_request.head.sha }}
          PR_LABELS: ${{ join(github.event.pull_request.labels.*.name, ',') }}
        run: |
          set -euo pipefail
          python3 - <<'PY'
          import os
          import pathlib
          import re
          import subprocess
          import sys

          base = subprocess.check_output(
              ["git", "merge-base", os.environ["BASE_SHA"], os.environ["HEAD_SHA"]],
              text=True,
          ).strip()
          head = os.environ["HEAD_SHA"]

          text = pathlib.Path("INDEX.md").read_text(encoding="utf-8")
          links = re.findall(r"\]\((courses/[^)#\s]+?)/?\)", text)
          labels = {x.strip() for x in os.environ.get("PR_LABELS", "").split(",") if x.strip()}
          dup_ok = "dup-ok" in labels
          errors = []
          warnings = []

          seen = set()
          for link in links:
              target = pathlib.Path(link.rstrip("/"))
              if not target.is_dir():
                  errors.append(f"INDEX.md 链接不存在：{link}")
              if link in seen:
                  errors.append(f"INDEX.md 重复链接：{link}")
              seen.add(link)

          course_dirs = set()
          for readme in pathlib.Path("courses").rglob("README.md"):
              course_dirs.add(readme.parent.as_posix())
          missing = sorted(course_dirs - seen)
          if missing:
              warnings.append(
                  "以下课程目录未出现在 INDEX.md（请运行 python3 scripts/build_index.py 重新生成）："
                  + ", ".join(missing[:20])
                  + (" ..." if len(missing) > 20 else "")
              )

          def tree_blobs(rev):
              out = subprocess.check_output(["git", "ls-tree", "-r", "-z", rev])
              result = {}
              for record in out.split(b"\0"):
                  if not record:
                      continue
                  meta, path = record.split(b"\t", 1)
                  mode, kind, oid = meta.split()
                  if kind == b"blob" and mode != b"120000":
                      result[oid.decode()] = path.decode("utf-8", "replace")
              return result

          base_blobs = tree_blobs(base)
          changed = subprocess.check_output(
              ["git", "diff", "--name-only", "-z", base, head]
          ).split(b"\0")
          seen_in_pr = {}
          for raw in changed:
              if not raw:
                  continue
              path = raw.decode("utf-8", "replace")
              if not path.startswith("courses/") or path.endswith(("README.md", ".gitkeep")):
                  continue
              tree = subprocess.check_output(
                  ["git", "ls-tree", head, "--", path], text=True
              ).strip()
              if not tree:
                  continue
              oid = tree.split("\t", 1)[0].split()[-1]
              if oid in seen_in_pr:
                  message = f"同一 PR 内重复文件（内容完全相同）：{seen_in_pr[oid]} 与 {path}"
                  if dup_ok:
                      warnings.append(message + "（已由维护者标记 dup-ok）")
                  else:
                      errors.append(message)
              seen_in_pr[oid] = path
              if oid in base_blobs and base_blobs[oid] != path:
                  warnings.append(
                      f"与库内已有文件内容相同：{path} 与 {base_blobs[oid]}"
                  )

          if errors:
              for message in errors:
                  print(f"::error::{message}")
              sys.exit(1)
          for message in warnings:
              print(f"::warning::{message}")
          print(f"索引检查通过：{len(links)} 个链接，{len(course_dirs)} 个课程目录。")
          PY
```

**接入分支保护的顺序（很重要）：**

1. 先由 owner 在 `type:governance` PR 中加入 workflow，但**不要**立刻设 required checks。
2. 用一个测试 PR 或 `workflow_dispatch`（可临时加）确认 `path-policy`、`content-check`、`index-dedupe` 都能出结果。
3. 到 `Settings → Branches → main` 勾选 `Require status checks`，搜索并选中上述三个名字。
4. 再开 `Do not allow bypassing`。顺序反了会把所有 PR 卡在「Expected」状态。
5. 不要给 workflow 加 `paths` 过滤；required check 被跳过时会一直显示 Expected，导致永远合不了。

### 3.3 Workflow 安全底线

| 底线 | 为什么 |
|---|---|
| 只用 `pull_request`，不用 `pull_request_target` + checkout PR 代码 | `pull_request_target` 运行在 base 上下文且有写 token，checkout 不可信 PR 代码等于把仓库交给攻击者 |
| `permissions: contents: read` | 检查只需要读；不需要写 issue/PR/内容 |
| `persist-credentials: false` | 不让 checkout 把 token 留在 git config 里 |
| 不引用 secrets | fork PR 不应该拿到任何秘密；需要评论/打标签的 bot 另做，且不 checkout PR 代码 |
| action 锁完整 SHA | tag 可被移动；SHA 不会 |
| 用 base 分支的 `scripts/check.sh` | PR 可以改自己仓库里的脚本，不能让它决定自己是否通过 |
| 不在 PR 里执行上传的代码/Office 宏 | 检查是静态的；打开宏等于执行恶意代码 |
| 失败信息写清路径和原因 | 作者能自己修，减少往返；维护者不用猜 |

### 3.4 自动化的边界

自动检查**不能**判断：

- 扫描件/图片里的姓名、学号、成绩（像素不是文本）；
- Word/PDF 的批注、修订记录、隐藏作者、文档属性是否真的清干净；
- 老师是否口头说过「不许外传」；
- 这份笔记是否真的有用、是否抄了教材图表；
- 文件是否带 0day/恶意 PDF 脚本。

所以：**自动失败 = 一定不能合；自动通过 ≠ 可以合。** 人工审核必须看 C 节。

## 4. C. 人工审核 SOP

### 4.1 时限与优先级

| 类型 | 首次回应 | 处理完成 | 为什么 |
|---|---|---|---|
| 恶意破坏/账号被盗 | 2 小时内冻结合并/撤权 | 24 小时内止损 | 破坏在持续发生，先止血 |
| 隐私/版权投诉 | 24 小时内确认并临时下架 | 48 小时内删除 | 公开多一小时，传播多一小时；先下架再讨论 |
| 普通上传 PR | 48 小时内 | 7 天内合并/关闭 | 学生维护者要上课；但也不能让作者等一个月 |
| 填表上传分诊 | 48 小时内 | 确认后加 `approved` 交给机器人；不能处理的关闭 | 防止 Issue 变成第二个垃圾场 |
| 作者 14 天不回应 | 关闭并留言「可随时重开」 | — | 防止 PR 队列腐烂；不惩罚作者 |

**单人维护的现实排法：** 每周固定 2 次、每次 30 分钟处理 PR/Issue；投诉随时插队。不要承诺「24 小时内合并」，只承诺「48 小时内首次回应」。

### 4.2 一个 PR 到手后的固定顺序

> 顺序不能反：先看路径（是不是这个库的东西），再看命名，再看隐私，再看版权，再看体积，最后才看内容有没有用。先看内容容易被「看起来很有用」带着合并，漏掉隐私和版权。

| 步骤 | 看什么 | 具体动作 | 直接拒/要求改 |
|---|---|---|---|
| **1. 路径** | 是否只改 `courses/`；公共课两层、专业课四层（学院/专业/课程）；有没有改 `.github/`、`scripts/`、`LICENSE`、`README.md` | 看 PR 的 `Files changed` 文件列表；用 `git diff --name-status main...PR` 确认 A/M/D/R | 改治理文件、根目录、symlink/submodule → 直接拒；路径错 → 要求改 |
| **2. 命名** | `YYYY春/秋-类型-描述.扩展名`；类型是否在固定集合；有没有空格/奇怪符号 | 对照 `CONTRIBUTING.md` 的命名规范；检查文件是否放在 `笔记/课件/试卷/作业` 正确子目录 | 命名乱 → 要求改；批量命名乱 → 可代改，但要在 PR 里说明 |
| **3. 个人信息** | 文件名、页眉页脚、封面、成绩栏、页边截图、Word/PDF 属性、批注/修订、图片 EXIF | 逐页看；跑 C.4.3 的命令；检查 `docProps/core.xml`、`pdfinfo`、`exiftool`；看有没有同学姓名/学号/组员/老师联系方式 | 有未脱敏个人信息 → **直接拒**，要求重传；不要「先合并再脱敏」 |
| **4. 版权** | 老师是否明确禁传；是不是未公开试卷/教材 PDF/教师用书/付费论文；图片表格来源 | 看水印、页脚、课程群公告；问作者要「来源 + 许可」；没有许可的课件/原卷默认不收 | 明确禁传/教材 PDF/未公开原卷 → 直接拒；许可不明 → 要求补充，补不了就拒 |
| **5. 体积与格式** | 单文件 ≤50 MiB；压缩包 ≤20MB；不是可执行/宏文档；不是 0 字节；总大小合理 | 看文件大小；下载前先看 GitHub 是否提示大文件；压缩包要求解压 | 超限压缩包/宏 → 要求拆分或改网盘；不解释就拒 |
| **6. 内容价值** | 是否与这门课有关；是不是广告/二维码/拉群；是否重复；是否可读 | 抽看首尾页/目录；搜关键词；和已有文件比哈希；看是否只有封面没有内容 | 无关/广告/空壳 → 拒；重复 → 要求说明或拒；低质量但真实 → 可收并标注 |

### 4.3 本地拉 PR 与检查命令

```bash
# 只读拉取 PR；不要 push 到别人的分支
git fetch origin pull/PR_NUMBER/head:pr-PR_NUMBER
git switch pr-PR_NUMBER

# 看这个 PR 相对 main 到底改了什么（三点 diff）
git diff --stat main...pr-PR_NUMBER
git diff --name-status main...pr-PR_NUMBER

# 看被修改文件的原内容，防止覆盖
git show main:'courses/.../README.md'
```

**PDF / Word / 图片隐私检查：**

```bash
# PDF 元数据（作者、标题、创建工具）
pdfinfo file.pdf
exiftool file.pdf

# Word/PPTX 核心属性（作者、最后修改人）
unzip -p file.docx docProps/core.xml
unzip -p file.pptx docProps/core.xml

# Word 批注/修订作者
unzip -p file.docx word/comments.xml 2>/dev/null | grep -o 'w:author="[^"]*"' | sort -u
unzip -p file.docx word/document.xml | grep -o 'w:author="[^"]*"' | sort -u

# 图片 EXIF（GPS、设备、作者）
exiftool image.jpg

# 文件哈希（和已有文件比对）
sha256sum file.pdf
```

> 不要在自己的常用电脑上直接打开来源不明的 `.docm/.xlsm/.pptm/.exe/.pdf`。需要看内容时，用浏览器预览/隔离环境；宏文档直接拒。不要为了审核把含个人信息的文件上传到第三方在线转换器。

### 4.4 决策表：直接拒 / 要求改 / 接收

| 结论 | 情形 | 动作 |
|---|---|---|
| **直接拒（Close）** | 恶意删卡/骂人/覆盖；广告、拉群、代考代写；与课程无关；0 字节/空壳；超限压缩包/可执行/宏；>50 MiB 且不愿拆分；未脱敏姓名学号；老师明确禁传；教材 PDF/未公开原卷；改 workflow/LICENSE/根目录；symlink/submodule；伪造来源/许可 | 关闭 PR，写清一条最主要原因；保留链接；恶意/广告可 block/report |
| **要求改（Request changes）** | 路径错；命名乱；缺课程卡片/子目录；重复文件；文件太大但可拆；PDF 有作者名；Word 有批注；来源/许可没写 | 用 C.5 模板；作者改完 push 同一分支，checks 自动重跑；不要关 PR。普通上传不用作者改 `INDEX.md`，维护者合并后刷新即可 |
| **接收（Approve + Squash）** | 路径/命名正确；无个人信息；版权/许可清楚；≤50 MiB；内容与课程相关且可读；不是重复；索引由维护者刷新 | squash 合并；删除分支 |
| **转 Issue/私聊** | 文件太大、不想学 Git、含敏感信息不便公开 | 让作者走 Issue 只写文件清单，不贴文件本身；敏感信息走私密渠道 |

**「要求改」的边界：** 维护者可以代改文件名、移动目录、补课程卡片模板；**不要代改隐私内容**（比如替作者涂掉姓名），因为维护者无法确认是否涂全，责任也不该由维护者单独承担。

### 4.5 审核话术模板

**路径/命名：**

```text
@作者 这个 PR 的方向没问题，但有两处需要改：
1. 文件应放在 courses/公共课/高等数学/试卷/，现在在 courses/公共课/高等数学/ 根目录；
2. 文件名请改成 2025秋-期末-高等数学A卷.pdf。
改完直接 push 到同一个分支即可，checks 会自动重跑，不用关 PR。
```

**个人信息：**

```text
@作者 文件第 X 页/文档属性里有姓名/学号，按仓库规则不能合并。
请删除后重传，并确认：PDF 属性、Word 作者/批注/修订记录、图片 EXIF 都已清理。
不要只裁掉页面边缘；如果原件是扫描件，请逐页检查。
```

**版权：**

```text
@作者 这份课件/试卷无法确认教师允许公开，按仓库规则先不收。
如果你能提供教师明确同意公开的说明（可打码个人信息），请补充到 PR 描述；
否则建议只上传你自己整理的笔记/复习提纲。教材 PDF 一律不收。
```

**体积/压缩包：**

```text
@作者 单文件上限 50 MiB，压缩包上限 20MB。
请拆分后重传，或把大文件放网盘，在课程 README 里登记「链接 + SHA256 + 有效期」。
仓库只保留索引和小文件。
```

**重复/覆盖：**

```text
@作者 这个文件和库里已有的 <路径> 内容完全相同（哈希一致）。
如果是同一份资料，请不要再传；如果是更新版，请说明改了什么，并把旧文件一起替换。
另外，你的分支似乎落后于 main，请先点 Update branch 再确认没有覆盖后来提交的内容。
```

**恶意/广告：**

```text
这个 PR 与课程资料无关/包含广告，按仓库规则关闭。
如属误操作，请阅读 CONTRIBUTING.md 后重新提交一个只改 courses/ 的 PR。
```

**投诉：**

```text
已收到，我们先做临时下架，24 小时内确认，48 小时内完成处理。
请不要在公开 Issue 里填写姓名、学号、电话等个人信息；后续走非公开渠道。
```

### 4.6 隐私/版权事故的应急顺序

1. **先冻结**：暂停合并相关 PR；不要继续在公开 Issue 里讨论细节。
2. **留证据**：记录文件路径、commit SHA、PR 号、发现时间；截图只截必要部分，别把个人信息再传播一次。
3. **先下架**：从 `main` 删除文件/条目（revert 或新提交），24 小时内给投诉人确认。
4. **判断是否重写历史**：
   - 只是版权投诉：先删当前文件 + 索引；权利人要求彻底清除再重写。
   - 姓名/学号/身份证/密钥：必须重写历史，否则 `git log` 仍能拿到。
5. **重写历史**：备份 → `git filter-repo`/BFG → force push（break-glass）→ GitHub Support 清理缓存 → 通知已知 fork 重建。
6. **通知与复盘**：在仓库公告「某路径已下架」，不公开投诉人信息；48 小时内记录原因和后续规则。

> 现有 `TAKEDOWN.md` 说「私密 Issue」，但普通 Issue 是公开的。上线前应改为「邮箱或 Private vulnerability reporting」，并且不要在 Issue 模板里收集个人信息。这个文件本次不改，但必须在下一次治理 PR 中修正。

## 5. D. 灾难恢复

### 5.1 通用原则

| 原则 | 为什么 | 怎么做 |
|---|---|---|
| 先备份再操作 | 恢复过程中第二次误操作会把唯一副本也弄没 | 任何 rewrite/reset 前先 `git clone --mirror` + bundle |
| 能 revert 就不 reset | revert 保留历史，别人 fork 还能对齐；reset 会让所有人历史分叉 | 内容回退用 revert；只有泄露隐私/密钥才 rewrite |
| 恢复成新分支，不直接改 `main` | 新分支可检查、可 PR、可回滚 | `rescue/...` 分支 → PR → 合并 |
| 一次只做一件事 | 同时 revert + rebase + force 会把问题叠加 | 先冻结，再恢复，再验证，最后解冻 |
| 记录操作 | 学生维护者也会忘；下次事故需要知道上次怎么救的 | 私密 incident log：时间、SHA、命令、结果，不写个人信息 |

### 5.2 撤销一次合并（误合并/恶意 PR 已合入）

> 下面命令里的 `MERGE_SHA`、`SQUASH_SHA`、`DELETE_SHA`、`OLD_SHA`、`GOOD_SHA`、`DATE`、`NAME`、`PR_NUMBER` 都是占位符；执行前整体替换成实际值。不要原样粘贴带 `<...>` 的写法。


**先判断是哪种合并：**

```bash
git fetch origin
git switch main
git pull --ff-only
git log --oneline --merges -n 10
git show -s --pretty=raw MERGE_SHA   # 看 parents 哪一个是 main
```

**情况 A：普通 merge commit（有两个 parent）**

```bash
git switch -c revert/MERGE_SHA
git revert -m 1 MERGE_SHA
# 如果冲突：编辑冲突文件 -> git add -A -> git revert --continue
# 放弃：git revert --abort
git push -u origin HEAD
```

然后在 GitHub 开 PR，等 checks 通过后 squash 合并。`-m 1` 的意思是「保留第一父提交（通常是 `main`）的版本」，不是盲目选 ours；如果不确定 parent 顺序，先看 `git show -s --pretty=raw MERGE_SHA`。

**情况 B：squash commit（只有一个 parent）**

```bash
git switch -c revert/SQUASH_SHA
git revert SQUASH_SHA
git push -u origin HEAD
```

**情况 C：连续多个坏提交**

```bash
git switch -c revert/batch-DATE
git revert --no-commit OLDEST_BAD_SHA^..NEWEST_BAD_SHA
git commit -m "revert: 撤销 OLDEST_BAD_SHA..NEWEST_BAD_SHA 的破坏性提交"
git push -u origin HEAD
```

如果范围里包含 merge commit，`git revert` 会要求 `-m`，不要硬套；拆成单个提交分别 revert。

**情况 D：整个树被搞坏，想恢复到某个已知良好提交**

```bash
git switch -c rescue/tree-DATE GOOD_SHA
git diff --stat main...HEAD   # 确认差异
git push -u origin HEAD
```

开 PR 合并。这样不会改写 `main` 历史；如果必须让历史也回到过去，才走 5.6 的 rewrite/force 流程。

### 5.3 找回被误删的文件/课程卡片

**先找删除提交：**

```bash
git log --all --full-history --diff-filter=D \
  --name-status --date=short --pretty=format:'%h %ad %s' \
  -- ':(glob)courses/**'
```

**找某个具体文件：**

```bash
git log --follow --name-status -- 'courses/公共课/高等数学/README.md'
git show --stat DELETE_SHA
```

**从删除前一个提交恢复：**

```bash
git switch -c restore/NAME
git restore --source="DELETE_SHA^1" -- 'courses/公共课/高等数学/README.md'
# 或整个目录
git restore --source="DELETE_SHA^1" -- 'courses/公共课/高等数学/'
git add -A
git commit -m "restore: 找回误删的 高等数学 课程卡片"
git push -u origin HEAD
```

**如果文件被重命名：**

```bash
git log --follow --name-status -- 'courses/.../旧文件名'
git show "RENAME_SHA^:courses/.../旧文件名" > /tmp/old-file
```

**如果删除还没提交：**

```bash
git restore -- 'courses/...'
# 已经 git add 过：
git restore --staged --worktree -- 'courses/...'
```

**如果文件从未提交过：** Git 里没有，无法恢复；只能找作者 fork、聊天记录、回收站。这也是为什么「先提交再改」很重要。

### 5.4 找回误删的分支

**本地 reflog：**

```bash
git reflog --all --date=iso | grep BRANCH_NAME
git branch rescue/BRANCH_NAME OLD_SHA
git push origin rescue/BRANCH_NAME
```

**PR 的 head ref（分支删了但 PR 还在）：**

```bash
git fetch origin 'refs/pull/*/head:refs/remotes/origin/pr/*'
git branch rescue/pr-PR_NUMBER origin/pr/PR_NUMBER
git push origin rescue/pr-PR_NUMBER
```

**镜像备份：**

```bash
git -C ~/course-vault-backup/repo.git branch --list
git -C ~/course-vault-backup/repo.git log --all --oneline --decorate -n 30
```

GitHub 网页偶尔会提供已删除分支的 `Restore`，但**不要把它当唯一方案**；真正可靠的是本地 reflog、PR ref 和镜像。

### 5.5 误 force push 后怎么救

**第一步：不要再 force push，先备份当前状态。**

```bash
cp -a .git "/tmp/course-vault-git-backup-$(date +%s)"
```

**第二步：在 reflog / 本地镜像里找旧提交。**

```bash
git reflog --all --date=iso
git reflog show origin/main 2>/dev/null || true
git fsck --full --unreachable --no-reflogs 2>/dev/null | head -50
```

如果看到旧提交：

```bash
git cat-file -t OLD_SHA
git branch rescue/main-DATE OLD_SHA
git push origin rescue/main-DATE
```

**第三步：如果旧提交只在 GitHub 上：**

- 先看有没有相关 PR：`git ls-remote origin 'refs/pull/*/head'`，PR 的 head ref 可能还指向旧提交；
- 看 GitHub 仓库的 `Insights → Network` / 分支活动，确认有没有旧 SHA；
- 联系 GitHub Support，说明仓库、分支、时间、SHA，请其协助恢复。**不保证一定恢复**，所以平时必须有本地镜像。

**第四步：恢复 `main`。**

- 只是内容坏了：从 `rescue/main-DATE` 开 PR，把好内容合回 `main`；历史里仍有坏提交，但内容正确。
- 必须让历史也回退（例如泄露了隐私）：走 5.6 的 rewrite，不要用普通 force push 当日常操作。

**为什么不能直接 `git push --force origin main`：** 会把别人在这段时间提交的内容一起覆盖，且分支保护通常会拒绝；即使成功，也破坏所有 fork 的同步基础。

### 5.6 隐私/密钥泄露后的历史重写（break-glass）

> 只有两种情况值得重写：**个人信息/密钥已经进入公开历史**，或权利人明确要求彻底清除。普通误删/误合并用 revert，不要重写。

```bash
# 0. 冻结合并，先做镜像和 bundle
git clone --mirror https://github.com/7620qwertqwert-beep/course-vault.git course-vault-mirror.git
git -C course-vault-mirror.git bundle create course-vault-before-rewrite.bundle --all
git bundle verify course-vault-before-rewrite.bundle

# 1. 在临时克隆里重写（不要在唯一工作副本上做）
git clone https://github.com/7620qwertqwert-beep/course-vault.git course-vault-rewrite
cd course-vault-rewrite
git filter-repo --path 'courses/.../含隐私文件.pdf' --invert-paths

# 2. 检查还有没有残留
git log --all --oneline -- 'courses/.../含隐私文件.pdf'
git grep -n '学号\|身份证\|手机号' $(git rev-list --all) -- 'courses/**' || true

# 3. 临时关闭/绕过 main 保护后强推（必须记录时间、原因、操作者）
git push --force --mirror origin

# 4. 立即恢复保护；通知 fork 持有者重新 clone/fetch；联系 GitHub Support 清理缓存
```

**注意：**

- `git filter-repo` 会改写所有相关提交 SHA；所有 fork 都会分叉，必须发公告让贡献者重新 clone。
- `--force --mirror` 会删除远端多出来的 ref，风险极高；只对确认过的镜像/临时仓库用。恢复单个分支用 `git push --force-with-lease origin RESCUE_BRANCH:main`，并先确认没有别人的新提交。
- GitHub 的缓存、fork、搜索引擎、第三方镜像不保证同步删除；能做的都做，但不能承诺「网上彻底没有了」。

### 5.7 备份方案：本地裸仓库 + 定期 bundle（无经费版）

**目标：** GitHub 挂了/账号丢了/历史被 rewrite，仍有一份可恢复的完整 Git 历史。公开仓库不等于备份——GitHub 是主副本，不是唯一副本。

| 项目 | 建议 | 为什么 |
|---|---|---|
| 本地裸仓库 | `git clone --mirror` 到自己的电脑/移动硬盘 | 包含所有分支、tag、完整历史；比工作副本干净 |
| 更新频率 | 每天 `git remote update --prune`；每周生成 bundle | fetch 很便宜；bundle 是单文件，方便复制 |
| 保留 | 最近 8 个周 bundle + 3 个月 bundle | 防「几周后才发现被改」；不需要无限占空间 |
| 异地 | 移动硬盘 + 另一个云盘/另一台电脑 | 3-2-1：GitHub + 本地 + 离线；无经费也能做到 |
| 验证 | 每月 `git bundle verify`；每季度真实恢复一次到临时目录 | 没验证过的备份等于没有备份 |
| 加密 | 含个人信息/密钥的备份用加密盘或 `gpg` | 备份本身也可能泄露隐私 |
| 不覆盖 | Issues/PR/Discussions/Release 附件/网盘链接不在 Git 里 | 这些要单独导出或至少记录；bundle 不包含它们 |

**初始化镜像：**

```bash
mkdir -p "$HOME/course-vault-backup"
git clone --mirror https://github.com/7620qwertqwert-beep/course-vault.git \
  "$HOME/course-vault-backup/repo.git"
```

**每日更新 + 每周 bundle：**

```bash
set -euo pipefail
BACKUP="$HOME/course-vault-backup"
REPO="$BACKUP/repo.git"
STAMP="$(date +%F)"

git -C "$REPO" remote update --prune
git -C "$REPO" bundle create "$BACKUP/course-vault-$STAMP.bundle" --all
git bundle verify "$BACKUP/course-vault-$STAMP.bundle"
git -C "$REPO" fsck --full

# 只保留最近 90 天的 bundle；重要节点另存
find "$BACKUP" -maxdepth 1 -name 'course-vault-*.bundle' -mtime +90 -delete
```

**cron 示例（按自己的电脑改时间）：**

```cron
# 每天 03:10 更新镜像
10 3 * * * git -C "$HOME/course-vault-backup/repo.git" remote update --prune >> "$HOME/course-vault-backup/fetch.log" 2>&1

# 每周日 03:30 生成并校验 bundle
30 3 * * 0 cd "$HOME/course-vault-backup" && git -C repo.git bundle create "course-vault-$(date +\%F).bundle" --all && git bundle verify "course-vault-$(date +\%F).bundle" >> bundle.log 2>&1
```

**恢复演练（每季度一次，恢复到临时目录，不要碰生产）：**

```bash
git clone "$HOME/course-vault-backup/course-vault-2026-01-04.bundle" /tmp/course-vault-restore
cd /tmp/course-vault-restore
git fsck --full
git log --oneline -5
git remote -v
```

**从 bundle 恢复到新仓库：**

```bash
git clone course-vault-YYYY-MM-DD.bundle /tmp/restored
cd /tmp/restored
git fsck --full
git remote set-url origin https://github.com/NEW_REPO_URL.git
git push origin --all
git push origin --tags
```

不要对已有仓库直接 `git push --mirror`（会删掉远端多出来的 ref）；恢复到**空仓库**时才考虑 `--mirror`。

### 5.8 Break-glass 操作卡（保护规则挡住恢复时）

1. 在仓库置顶 Issue 公告「维护中，暂停合并」，不要写敏感细节。
2. 先做镜像 + bundle；记录当前 `main` SHA。
3. 只关闭挡住恢复的那一条规则（优先用 ruleset 的临时 bypass，而不是整条删除）。
4. 60 分钟内完成最小修复；不做顺手重构。
5. 立即恢复规则；用一个测试 PR 验证 `main` 仍然不能直推/force/删除。
6. 24 小时内写事故记录：原因、时间线、影响文件、恢复命令、如何防再次发生。
7. 如果是账号被盗：改密码、撤销会话、移除协作者、检查 Actions secrets/Deploy keys/Webhooks，必要时轮换所有 token。

| 索引同步 | 已实现（2026-10） | 新增课程后由维护者运行 `python3 scripts/build_index.py`；普通上传不用作者改；CI 的 `--check` 兜底 |
| 标签体系 | 建 6–10 个核心标签 | `type:upload/meta/governance/cleanup`、`risk:privacy/copyright/size`、`needs-author`、`dup-ok` |
| 每周固定审核时段 | 固定 | 10 个贡献者时 PR 会开始堆积；固定 2×30 分钟比随时被打断可持续 |
| 备份 | 每日 mirror + 每周 bundle + 月度恢复演练 | 资料开始变多，丢一天的提交也会疼 |
| 大文件外链 | >10 MiB 的二进制优先外链 | 控制 clone 体积；为后期千门课做准备 |

### 6.4 后期（全校上千门课）该做的架构调整

| 调整 | 为什么 | 怎么做 |
|---|---|---|
| 转 GitHub Organization | 个人仓库没有团队、组织审计日志、细粒度团队权限 | 迁到学校/社团 Org；用 Teams 分学院；保留 owner 2–3 人 |
| Git 只存「卡片 + 索引 + 清单」 | 上千门课 × 课件/试卷会把仓库撑到几 GB，clone/fork 都痛苦 | 大文件放学校对象存储/网盘/Release，仓库存 `manifest`（路径、SHA256、来源、许可、失效日期） |
| 不用 Git LFS 当主方案 | 免费 1GB 存储/1GB 月流量，课程资料很快超 | 除非学校提供 LFS/对象存储；否则外链 + 哈希校验 |
| 分学院 CODEOWNERS | 中心维护者不可能懂所有专业 | 每个学院 1–2 个 Maintain/Write；核心维护者保留治理文件 |
| 审核分级 | 全量 2 人审批会堵死 | 日常小新增：1 批准 + 检查；治理/批量删除/版权风险：2 人 + 公告 |
| 索引自动生成 | 手改 INDEX 必然冲突 | 已实现：`scripts/build_index.py` 从课程目录生成，CI `--check` 校验；PR 不手改 INDEX |
| 季度访问审计 | 长期项目最大的风险是「忘了谁还有权限」 | 每季度列 Admin/Maintain/Write，移除不活跃的人；检查 deploy keys/webhooks/apps |
| 备份异地/加密 | 单盘损坏、电脑丢失 | 本地 mirror + 移动硬盘 + 加密云盘；每季度恢复演练 |

### 6.5 现在先别开的开关（避免流程重到没人传）

| 先别开 | 为什么现在不开 | 什么时候再开 |
|---|---|---|
| Required approvals ≥ 2 | 1 人时直接死锁；10 人时也常常凑不齐 | 有 5 个以上活跃 Maintain，且 PR 量稳定 |
| Require review from Code Owners（现在） | owner 自己是作者时无法自批，PR 永远卡住 | 每个关键目录至少 2 个有 Write 的 owner |
| Require signed commits | 网页上传/学生本地环境经常没配签名 | 有明确安全要求，且提供配置教程 |
| CLA / DCO | 法律文本、签署流程、存档都要人维护；无经费 | 学校法务/知识产权办公室介入时 |
| 强制所有 Issue 先填 10 项 | 新同学会被吓走；现在最缺的是供给 | Issue 量 >10/周，且垃圾占比高 |
| Auto-merge（非归档 PR） | 其他 PR 自动合并等于自动放行 | 只对 `approved` 归档 PR 开，其他 PR 保持人工 |
| 全库 2 人审批 | 上千门课时会变成瓶颈，最后没人审 | 只对治理/批量删除/版权高风险开 2 人 |
| Git LFS | 免费额度太小，配置和迁移成本高 | 学校提供 LFS/对象存储，或仓库转为机构组织 |
| 复杂的 Projects 看板 | 一个人维护看板是纯负担 | 有 2 个以上 Maintain 且 PR >20/周 |

### 6.6 阶段升级/回滚的触发条件

| 转换 | 触发条件（满足 2 项即可） | 动作 |
|---|---|---|
| 现在 → 中期 | 连续 30 天有 ≥3 个活跃贡献者；累计 ≥10 个合并 PR；有 1 个可信审核人；真实资料 >100 个文件 | 加 1 批准、Code Owners、Discussions、标签、每日备份 |
| 中期 → 后期 | ≥50 个贡献者；≥500 个合并 PR/年；仓库 >1GB 或课程 >1000；每天都有 PR | 转 Org、分学院团队、索引自动化、大文件外链、审核分级 |
| 回滚 | PR 平均等待 >7 天；维护者连续 2 周没时间审；贡献者明显流失 | 先关非安全类门槛（Code Owners/审批数/Discussions 分类），**不关** force push/删除保护/必过检查 |

**判断标准：** 流程的重量应该由「事故成本」决定，不是由「看起来正规」决定。删库/隐私泄露成本高，所以硬拦；命名不规范成本低，所以提示 + 人工改即可。

## 7. 附录

### 7.1 建议的标签（先建 8 个，不要一次建 30 个）

| 标签 | 用途 | 谁能加 |
|---|---|---|
| `type:upload` | 普通资料上传 | 模板自动/维护者 |
| `type:meta` | 课程卡片/索引/文档修改 | 维护者 |
| `type:governance` | 改 workflow/脚本/LICENSE/规则 | 仅 owner |
| `type:cleanup` | 删除/移动/重命名 | 维护者 |
| `risk:privacy` | 疑似个人信息 | 维护者 |
| `risk:copyright` | 疑似版权/禁传 | 维护者 |
| `needs-author` | 等作者修改 | 维护者 |
| `dup-ok` | 确认重复内容可保留 | 维护者 |
| `takedown` | 下架投诉（高优先级） | 维护者 |

> `dup-ok`、`type:governance` 这类「能让检查放行」的标签，只能由对仓库有 Triage/Write 以上权限的人加；普通 fork 作者不能给自己加。`type:governance` 还要求 PR 作者是 owner。

### 7.3 维护者每周 30 分钟检查表

- [ ] `git fetch origin && git log --oneline main..origin/main`：有没有绕过 PR 的直推？
- [ ] 看 `Settings → Branches`：保护规则还在？没有被人关掉？
- [ ] 看 `Settings → Access`：有没有陌生协作者/多余 Admin？
- [ ] 看 `Settings → Actions`：有没有新的 workflow/secret？
- [ ] 看最近合并的 10 个 PR：有没有删除/覆盖/隐私文件漏网？
- [ ] 跑一次 `bash scripts/check.sh`：当前 `main` 是否仍然通过？
- [ ] 做一次镜像 `git remote update --prune`；周日生成 bundle 并 `git bundle verify`。
- [ ] 清空/归档已处理的 Issue/PR，避免队列腐烂。

### 7.5 最后一句

治理的目标不是把仓库变成「谁都不敢传」，而是让**坏人一次只能造成很小的破坏，好人十分钟就能完成一次上传**。如果某条规则让好人的成本明显高于坏人的成本，就把它降级为警告或移到后期。
